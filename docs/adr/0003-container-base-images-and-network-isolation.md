# ADR-0003: Базові образи контейнерів та стратегія ізоляції мереж

- **Статус:** Accepted
- **Дата:** 2026-11-18
- **Контекст проєкту:** BookSwap (C4 Container View з лабораторної роботи 1: Web Application, Backend API, база даних, Redis-кеш, S3-сховище)
- **Пов'язані документи:** ADR-0001 (PostgreSQL), ADR-0002 (Redis cache-aside)

## Context

Під час переходу від діаграми C4 до робочого середовища потрібно вирішити:

1. Які базові образи використовувати для власних сервісів (Frontend, Backend).
2. Як розділити мережі між контейнерами, щоб дотримуватись принципу найменших привілеїв.

Вимоги: малий розмір образів, мінімальна поверхня атаки, запуск від non-root користувача, відтворюваність середовища, простота налагодження в навчальному проєкті.

## Розглянуті варіанти базових образів

| Варіант | Переваги | Недоліки |
|---|---|---|
| `*-alpine` (musl libc) | Дуже малий розмір (~50–60 МБ для Node), є shell та пакетний менеджер для налагодження й healthcheck | musl інколи несумісний з нативними бінарними модулями; менш поширений у production-середовищах із glibc |
| `*-slim` (Debian, glibc) | Максимальна сумісність із нативними залежностями | Більший розмір (~200 МБ), більше пакетів → більше CVE |
| `distroless` | Мінімальна поверхня атаки, немає shell | Складніше налагодження; healthcheck без shell потребує окремих рішень; надмірна складність для навчального проєкту |

## Розглянуті варіанти мережевої топології

| Варіант | Переваги | Недоліки |
|---|---|---|
| Одна спільна мережа (за замовчуванням у Compose) | Найпростіше | Скомпрометований Frontend бачить БД, Redis і S3 |
| **Дві мережі: `frontend-net` + `backend-net` (internal)** | Принцип найменших привілеїв, БД недосяжна ззовні та з Frontend | Налагодження БД лише через `docker compose exec` |
| Мережа на кожен сервіс | Максимальна ізоляція | Надмірна складність для 5 сервісів |

## Decision

### Образи

- **Backend:** `node:22-alpine`, multi-stage (етап `deps` встановлює залежності, етап `runtime` отримує лише `node_modules` і код). Користувач `node` (вбудований, non-root).
- **Frontend:** етап збірки на `node:22-alpine`, runtime на `nginxinc/nginx-unprivileged:1.27-alpine` (non-root, порт 8080 замість привілейованого 80). У фінальний образ потрапляє лише статика.
- **БД і кеш:** офіційні `postgres:17-alpine`, `redis:7-alpine`.
- **MinIO** (локальна заміна S3): образ фіксується на конкретному релізі (не `latest`) для відтворюваності.
- `distroless` відкладено як майбутнє покращення для Production; у коді немає нативних модулів, тож перехід буде простим.

Alpine обрано через баланс розміру та можливості виконувати healthcheck (`wget`, `node -e`) без додаткових інструментів.

### Мережі

- `frontend-net` — Frontend і Backend.
- `backend-net` (`internal: true`) — Backend, PostgreSQL, Redis, MinIO.

Backend — єдиний сервіс в обох мережах і діє як шлюз. Назовні опубліковано лише порт Frontend; запити до `/api` проксуються nginx-ом на Backend.

### Спрощення відносно ADR-0001

ADR-0001 обирає PostgreSQL з PostGIS, а локальне середовище лабораторної роботи 2 використовує `postgres:17-alpine` без PostGIS, а місто зберігається текстовим полем. Це свідоме спрощення: геопошук за відстанню заплановано на спринт 3, тоді образ БД буде замінено на `postgis/postgis`.

### Додаткові рішення

- Уся конфігурація передається змінними оточення з `.env` (12-Factor, фактор III); `.env` не комітиться, у репозиторії лише `.env.example`. Обов'язкові змінні без значення зупиняють запуск (`${VAR:?}`).
- Дані зберігаються в іменованих томах (`pgdata`, `redisdata`, `miniodata`).
- Порядок запуску: `depends_on` з `condition: service_healthy` для БД, Redis і Backend.
- Backend обробляє SIGTERM (graceful shutdown, фактор IX); у Compose `init: true`.

## Consequences

**Позитивні:**

- Малі образи, непривілейовані процеси, відтворюваний запуск однією командою (`docker compose up --build`).
- PostgreSQL, Redis та MinIO недоступні з Frontend-контейнера та з хоста: порти не публікуються, мережа `internal` не має виходу назовні. Скомпрометований Frontend не має мережевого шляху до БД.

**Негативні / компроміси:**

- Мережа `internal` не дозволяє БД, Redis і MinIO виходити в інтернет (наприклад, для оновлень); для локального середовища це прийнятно.
- Для налагодження БД потрібен `docker compose exec db psql ...`, а не прямий доступ із хоста.
- Alpine (musl) може створити проблеми при додаванні нативних модулів — тоді слід перейти на `slim`.
- Мінімальна відмінність від production: там БД і Redis керовані (RDS, ElastiCache), а ізоляцію забезпечують VPC і security groups, а не мережі Docker.
