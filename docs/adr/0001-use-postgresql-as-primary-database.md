# ADR-0001: Використання PostgreSQL (з PostGIS) як основної бази даних

- **Статус:** Accepted
- **Дата:** 2026-11-01
- **Автор(и):** Андрій
- **Пов'язані вимоги:** NFR-02 (продуктивність), NFR-03 (доступність), NFR-05 (приватність), NFR-07 (відновлюваність), US-06, US-07

## Context

BookSwap зберігає взаємопов'язані дані: користувачі, книги, заявки на обмін, відгуки, скарги. Для заявок потрібна **транзакційна цілісність** (наприклад, не можна прийняти дві заявки на одну книгу одночасно). Ключова функція — **пошук книг поруч** (геофільтр за відстанню) разом із повнотекстовим пошуком за назвою й автором. Читання переважає над записом (~90/10), обсяг даних помірний (десятки тисяч користувачів, сотні тисяч книг).

Розглянуті варіанти:

1. **PostgreSQL + PostGIS**
2. **MySQL / MariaDB**
3. **MongoDB**
4. PostgreSQL + окремий пошуковий рушій (Elasticsearch / OpenSearch)

## Decision

Обираємо **PostgreSQL (версія 16) з розширенням PostGIS** як єдине основне сховище даних. У production використовуємо керований сервіс **Amazon RDS** у режимі Multi-AZ.

Обґрунтування:

- Реляційна модель природно підходить для домену (користувач — книга — заявка), підтримує ACID-транзакції та обмеження цілісності (FK, UNIQUE, CHECK).
- **PostGIS** дає геопошук (`ST_DWithin`, GiST-індекси) без додаткових систем.
- Вбудований повнотекстовий пошук (`tsvector`, GIN) і `pg_trgm` достатні для пошуку за назвою/автором на очікуваних обсягах.
- Зріла екосистема: міграції (Flyway/Prisma), бекапи, PITR, моніторинг (`postgres_exporter` для Prometheus).
- Безкоштовна ліцензія, відсутність vendor lock-in (RDS можна замінити на самостійне розгортання).

## Consequences

**Позитивні:**

- Одна система для транзакційних даних, геопошуку й текстового пошуку — менше інфраструктури та операційних витрат.
- Multi-AZ і автоматичні бекапи покривають NFR-03 та NFR-07.
- Прості інтеграційні тести через Testcontainers (реальний PostgreSQL в CI).

**Негативні / компроміси:**

- Горизонтальне масштабування запису складніше, ніж у NoSQL; для читання використовуємо Redis-кеш (ADR-0002) і за потреби read replicas.
- Повнотекстовий пошук PostgreSQL поступається Elasticsearch за релевантністю та мовними можливостями (морфологія української); якщо вимоги зростуть, додамо окремий пошуковий рушій і зафіксуємо новим ADR.
- Схема змінюється через міграції — вони мають бути частиною CI/CD-пайплайну та зворотно сумісними (expand/contract) для деплою без простою.
- Потрібне налаштування розширення PostGIS на RDS і в локальному `docker compose` (образ `postgis/postgis`).

## Alternatives considered

| Варіант | Чому відхилено |
|---|---|
| MySQL/MariaDB | Слабша підтримка геоданих і розширень порівняно з PostGIS |
| MongoDB | Домен реляційний, потрібні транзакції між сутностями; переваги гнучкої схеми тут не критичні |
| PostgreSQL + Elasticsearch | Надмірна складність і вартість на старті; повернемося до рішення, якщо пошук стане вузьким місцем |
