# ADR-0004: CI/CD платформа, версіонування артефактів і політика Quality Gates

- **Статус:** Accepted
- **Дата:** 2026-11-25
- **Пов'язано:** ADR-0003 (контейнеризація), NFR-04, NFR-08, NFR-09

## Контекст

Після Лабораторної 2 проєкт збирається локально через `docker compose`. Потрібно автоматично перевіряти кожну зміну
(NFR-08: merge → production ≤ 30 хв), блокувати вразливий або зламаний код (NFR-04) і отримувати відтворювані
незмінні артефакти для наступних середовищ («Build once, deploy anywhere», 12-Factor V).

## Рішення

### 1. Платформа: GitHub Actions + GitHub Container Registry (GHCR)
Код уже в GitHub; Actions не потребує окремого сервера; `GITHUB_TOKEN` з правом `packages: write` дозволяє
пушити в GHCR без довгоживучих паролів. Альтернативи: GitLab CI (вимагає міграції репозиторію), Docker Hub
(окремий секрет і ліміти pull).

### 2. Стратегія розгалуження: GitHub Flow
Єдина стабільна гілка `main`, короткоживучі `feature/*`, `fix/*`. Усі зміни — через Pull Request. Гілка `main`
захищена: заборона прямого push і force-push, обов'язкові status checks (актуальні відносно main), мінімум 1 approve,
вирішені коментарі, лінійна історія (squash merge). GitFlow відхилено як надмірний для веб-сервісу з частими
релізами; Trunk-Based потребує Feature Flags, яких у проєкті ще немає.

### 3. Версіонування образів
Кожен образ (`backend`, `frontend`) отримує теги:

| Тег | Коли | Незмінний |
|---|---|---|
| `sha-<7 символів SHA>` | кожен push у `main` та у тег | так, основний ідентифікатор для деплою |
| `X.Y.Z`, `X.Y` | git-тег `vX.Y.Z` (SemVer) | `X.Y.Z` так |
| `main` | push у `main` | ні, лише зручний покажчик |

Тег `latest` не публікується. Наступні середовища (Staging/Production) використовують лише `sha-…` або `X.Y.Z`
і не перезбирають код. На Pull Request образ збирається й сканується, але **не публікується**.

### 4. Політика Quality Gates
Усі гейти обов'язкові (required status checks), порядок — Fail Fast:

| Гейт | Інструмент | Умова провалу |
|---|---|---|
| Lint Dockerfile | hadolint | попередження рівня warning і вище |
| Lint / format коду | ESLint (`npm run lint`) | будь-яка помилка |
| Unit-тести | `npm test` | будь-який тест червоний |
| SCA + Secret Detection | Trivy `fs` | HIGH/CRITICAL CVE з наявним виправленням, або знайдений секрет |
| Сканування образу | Trivy `image` | HIGH/CRITICAL CVE з наявним виправленням (ОС і бібліотеки) |
| Build | Docker Buildx | помилка збірки |

Публікація (`docker push`) виконується лише після проходження всіх гейтів і лише для подій `push` (не PR).
Виняток для вразливості без виправлення — запис у `.trivyignore` з коментарем і терміном перегляду, через PR.
Поріг покриття тестами (≥ 80 %) вводиться, коли з'явиться достатня кількість тестів (див. наслідки).

### 5. Кешування
`actions/setup-node` кешує npm-залежності (ключ — хеш `package-lock.json`); шари Docker кешуються в
`type=gha` (scope окремо для кожного сервісу).

### 6. Секрети
Для GHCR використовується вбудований `GITHUB_TOKEN` з мінімальними правами (`contents: read` за замовчуванням,
`packages: write` лише в job `build`). Додаткових секретів у репозиторії немає. Dependabot оновлює залежності,
Dockerfile-базові образи та версії Actions.

## Наслідки

- (+) Кожна зміна верифікується однаково; вразливості виявляються до merge (Shift Left).
- (+) Артефакт збирається один раз і ідентифікується за SHA, відкат = деплой попереднього тегу.
- (−) Пайплайн залежить від GitHub (vendor lock-in у YAML-синтаксисі); образ по суті збирається двічі
  (scan → push), але другий раз повністю з кешу.
- (−) Для одного розробника вимога approve потребує або другого акаунта, або bypass адміністратора.
- (−) Гейти lint/test вимагають наявності відповідних npm-скриптів у `backend` і `frontend`.
- Подальше: SAST (CodeQL), перевірка покриття, підпис образів (cosign), автодеплой на staging (Лаб. 4+).
