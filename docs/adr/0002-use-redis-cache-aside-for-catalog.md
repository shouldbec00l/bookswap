# ADR-0002: Redis і патерн cache-aside для кешування каталогу

- **Статус:** Accepted
- **Дата:** 2026-11-01
- **Автор(и):** Андрій
- **Пов'язані вимоги:** NFR-01 (масштабованість читання), NFR-02 (продуктивність), NFR-06 (observability), US-06, US-07

## Context

Публічний каталог і пошук книг — найнавантаженіша частина системи: співвідношення читання до запису приблизно 90/10, ціль — до 500 RPS читання з p95 пошуку ≤ 300 мс. Геопошук (`ST_DWithin`) і текстовий пошук у PostgreSQL коштовні, а частина запитів повторюється (популярні жанри, пошуки в межах одного району). Пряме масштабування БД під пікове читання дороге й ускладнює доступність.

Розглянуті варіанти:

1. **Redis + cache-aside**
2. Кешування в пам'яті процесу API (in-process)
3. Read replicas PostgreSQL без кешу
4. HTTP-кеш/CDN для відповідей API

## Decision

Використовуємо **Redis** (Amazon ElastiCache, Primary + Replica у різних AZ) із патерном **cache-aside**:

1. API формує ключ `search:{hash(параметрів запиту)}` і читає з Redis.
2. **Cache hit** — повертає результат без звернення до БД.
3. **Cache miss** — виконує запит у PostgreSQL, записує результат у Redis із **TTL 60 с** і повертає відповідь.
4. При зміні даних (додавання/редагування/приховування книги, зміна статусу) відповідні ключі інвалідуються або чекають завершення TTL — допустима кінцева узгодженість до 60 с.

Додатково Redis використовується для **rate limiting** (лічильники запитів на IP/користувача).

Правила:

- Кеш не є джерелом істини; при недоступності Redis API **деградує до прямих запитів у БД** (graceful degradation), а не повертає помилку.
- Персональні дані (контакти учасників заявок) **не кешуються**.
- Експортуємо метрики `bookswap_cache_hits_total` / `bookswap_cache_misses_total` і відстежуємо cache hit ratio на дашборді Grafana.

## Consequences

**Позитивні:**

- Суттєво знижується навантаження на PostgreSQL та затримка популярних запитів — виконання NFR-01 і NFR-02.
- API лишається **stateless**: кеш спільний для всіх реплік, тому HPA працює без прив'язки клієнтів до подів.
- Redis одночасно закриває rate limiting (NFR-04).

**Негативні / компроміси:**

- Нова компонента в інфраструктурі: потрібні Terraform-модуль, моніторинг, оновлення, Multi-AZ (додаткова вартість).
- **Кінцева узгодженість:** користувач може до 60 с бачити застарілий результат пошуку; для критичних операцій (заявки, контакти) кеш не використовується.
- Складність інвалідації: помилки в ключах чи TTL можуть давати застарілі дані; потрібні тести та метрики.
- Ризик «cache stampede» при одночасному промаху популярного ключа; пом'якшуємо jitter у TTL і/або блокуванням перерахунку.
- Падіння Redis підвищує навантаження на БД — навантажувальні тести (k6) мають перевіряти сценарій без кешу.

## Alternatives considered

| Варіант | Чому відхилено |
|---|---|
| In-process кеш | Кожна репліка має власний кеш: низький hit ratio, неузгодженість між подами, ускладнює масштабування |
| Лише read replicas | Дорожче, не вирішує затримку геопошуку; можна додати пізніше |
| Лише HTTP-кеш/CDN | Відповіді залежать від параметрів і геолокації користувача — низька повторюваність; CDN використовуємо лише для статики й обкладинок |
